# Домашнее задание: разложите гибридный сервис

## Шаг 1. Компоненты сервиса

| Компонент | Роль в сервисе | Риск при отсутствии | Артефакт или проверка |
|---|---|---|---|
| DVC | Повторяемо выполняет подготовку данных, обучение churn-модели и создание отчёта мониторинга. | Данные, параметры и модель могут перестать соответствовать друг другу, а результат обучения будет трудно повторить. | Этапы описаны в `dvc.yaml`, их состояния и хеши зафиксированы в `dvc.lock`; в CI выполняются `dvc repro` и `dvc status`. |
| MLflow | Сохраняет параметры и метрики обучения, связывает модель с конкретным запуском и даёт ей версию. | Будет непонятно, какой запуск создал модель, обслужившую запрос, и чем версии отличаются друг от друга. | `src/churn_ml/training.py` создаёт запуск MLflow, а `models/model_metadata.json` хранит `mlflow_run_id` и контрольную сумму модели. |
| FastAPI | Принимает текст отзыва и признаки клиента, проверяет входные данные и возвращает sentiment и риск оттока. | У сервиса не будет стабильного контракта запроса и ответа, проверки входных значений и идентификатора запроса. | Эндпоинты `/predict` и `/health` находятся в `src/churn_ml/api.py`, их контракт проверяет `tests/test_contract.py`. |
| Docker | Упаковывает API и нужные ему библиотеки в одинаковое окружение для запуска. | Сервис может работать у разработчика, но не запускаться в другом окружении из-за различий Python и библиотек. | Образ задаёт `Dockerfile`, совместный локальный запуск API и MLflow — `docker-compose.yml`, а CI проверяет `docker build`. |
| CI | На pull request и push в `main` повторяет pipeline и проверяет тесты и сборку образа. | Ошибка в данных, модели, API или Docker-сборке может попасть в основную ветку незамеченной. | `.github/workflows/ci.yml` запускает `dvc repro`, `pytest`, `docker build` и сохраняет отчёты как результаты проверки. |
| Evidently | Офлайн сравнивает reference и current данные и показывает сдвиг их распределений. | Команда может не заметить, что новые данные стали отличаться от тех, на которых обучалась модель. | `src/churn_ml/monitoring.py` создаёт `reports/monitoring_report.html`; отчёт указан как результат стадии `monitor` в `dvc.yaml`. |

## Шаг 2. Два слоя мониторинга

| Слой | Что наблюдаем | Пример сигнала | Действие команды |
|---|---|---|---|
| Технический мониторинг | Доступность API и завершение запросов; в проекте этот слой реализован минимально через `/health`, request ID и логи. | `/health` недоступен, запрос завершился ошибкой или модель не готова. | Проверить логи API, состояние сервиса и доступность модели. |
| ML-мониторинг | Офлайн-сдвиг признаков и тональности между reference и current выборками. | Evidently показывает заметное изменение распределения активности, обращений в поддержку, NPS или sentiment. | Разобраться в источнике сдвига, проверить качество модели на current-данных и при необходимости переобучить её. |

Технический мониторинг отвечает на вопрос, работает ли сам сервис, а ML-мониторинг — остаются ли входные данные похожими на данные обучения. Исправный API всё равно может давать менее надёжные прогнозы при дрейфе данных, поэтому один слой не заменяет другой.

## Шаг 3. Путь одного запроса

Клиент отправляет в `/predict` текст отзыва и числовые признаки клиента, после чего FastAPI проверяет входные данные и назначает запросу `request_id`. API загружает подготовленную модель: DVC помогает повторяемо получить её из данных и параметров, а MLflow связывает модель с конкретным запуском и версией. Сначала sentiment-модель оценивает вероятность негативного отзыва, затем churn-модель объединяет её с признаками клиента и считает вероятность оттока. В ответе клиент получает прогноз, версию сервиса, версию кода, идентификатор запуска MLflow и контрольную сумму модели. Docker даёт сервису одинаковое окружение запуска, а CI заранее проверяет pipeline, API-тесты и сборку образа. После запроса минимальный технический мониторинг оставляет request ID и статус в логах, а Evidently отдельно и офлайн сравнивает reference/current данные, то есть напрямую этот запрос не наблюдает.
